# 经典伴奏保音高变速技术方案

## 1. 背景与问题

经典伴奏模式通过调整音频播放速率来匹配用户选择的 BPM。当前实现把 `AudioBufferSourceNode.playbackRate` 设为“目标 BPM / 原曲 BPM”。这个属性通过重采样加快或放慢采样，因此速度和音高会一起变化：加速会升调，减速会降调。Web Audio API 对该行为有明确说明：[MDN：AudioBufferSourceNode.playbackRate](https://developer.mozilla.org/en-US/docs/Web/API/AudioBufferSourceNode/playbackRate)。

相关代码：

- `src/utils/audioBackingTrack.ts`：计算播放速率并设置 `playbackRate`；A 调伴奏原始 BPM 为 125，起播偏移为 5 秒。
- `src/components/ChordPractice/index.tsx`：BPM 变化时调用 `adjustSpeed` 实时调速。

用户期望的是节奏随 BPM 改变，而伴奏仍保持原调。

## 2. 目标与范围

### 目标

- 调节 BPM 时保持伴奏的音乐音高不变。
- 保留当前音量、预加载、起播偏移、循环和调速交互。
- 避免用户拖动速度控件时反复重启伴奏。
- 对不支持推荐音频处理路径的浏览器提供不升降调的降级策略。

### 不在本次范围

- 新增其他调性的伴奏录音。
- 修改合成伴奏模式、鼓组或和弦进行逻辑。
- 增加后端处理或上传音频服务。

## 3. 推荐技术路线

在现有 Web Audio 管线中增加 AudioWorklet 保音高处理器。已集成并锁定 SoundTouchJS AudioWorklet `2.1.1`（MPL-2.0）；Vite 通过 `?url` 导入独立 processor 资源。该项目要求音源和处理器使用相同的 `playbackRate`，由处理器补偿因源速率产生的音高变化：[SoundTouchJS AudioWorklet 文档](https://github.com/cutterbl/SoundTouchJS/blob/master/packages/audio-worklet/README.md)。

推荐的处理链：

```text
AudioBufferSourceNode → AudioWorklet 时间拉伸处理器 → GainNode → AudioContext.destination
```

音源仍使用已预加载的 `AudioBuffer`，并继续负责起播偏移与循环；Worklet 负责时间拉伸和音高补偿；`GainNode` 保持现有音量控制。初始化 AudioContext 时注册 Worklet 模块，播放时创建音源和处理节点。

速度倍率按下式计算，并同时平滑设置 `AudioBufferSourceNode.playbackRate` 和 `SoundTouchNode.playbackRate`：

```text
rate = targetBPM / originalBPM
```

处理器接收与音源相同的 `rate`，目标音高保持原调（pitch multiplier = 1，pitch semitones = 0）。滑动调速时两个速率参数使用相同的 AudioContext 时间点和 30 ms 平滑常数；禁止只修改 `AudioBufferSourceNode.playbackRate` 而绕过补偿处理器。

## 4. 播放与调速流程

1. **初始化**：创建 AudioContext 和 GainNode；注册 AudioWorklet；复用现有逻辑预加载 A 调音频。
2. **开始播放**：以现有 5 秒起播偏移和循环区间创建 AudioBufferSourceNode；按当前 BPM 创建/连接时间拉伸处理器，再接至 GainNode。
3. **实时调速**：BPM 更新时，向处理器的 AudioParam 发送新速率；使用短时间平滑过渡，避免参数突变产生杂音。不重建 source、不重置循环位置。
4. **停止播放**：停止一次性 BufferSource，断开本次播放节点并清理事件/引用；保留已预加载的 AudioBuffer 和已注册的 Worklet。
5. **切换模式或调性**：沿用现有停止、加载和状态管理流程，避免旧 Worklet 节点继续输出。

## 5. 循环、延迟与音质

- 当前循环默认从 5 秒起至音频结尾。加入时间拉伸后，应实际验证循环点是否连续；若出现点击声或短暂空洞，再针对循环段做短交叉淡化或调整算法窗口。
- 时间拉伸处理器可能有启动延迟。要测量它相对节拍器的延迟，并确保鼓声、和弦提示和伴奏首拍仍同步；若不满足要求，应让三者以同一音频时钟调度，或在播放启动阶段补偿固定延迟。
- 时间拉伸可以保持音高，但极端变速可能出现瞬态模糊、颤动或其他处理痕迹。应使用真实 Blues 混音试听，而不能只用纯音验证。
- 当前 UI BPM 为 60–180，原曲为 125 BPM，对应倍率约为 0.48–1.44。修改前代码把倍率限制在 0.5–2.0，导致 60 BPM 实际只能达到 62.5 BPM；现实现改为覆盖 0.48–1.44。仍需通过真实录音试听确认两端音质；如最终限制范围，UI 显示和实际速度必须一致，不能静默夹限。

## 6. 降级策略

优先路径是 AudioWorklet 保音高处理。当前实现检测浏览器和处理器注册状态；不支持或加载失败时，显示错误并停止经典伴奏启动，不回退到会变调的播放方式。`<audio>` + `preservesPitch` 暂不作为自动降级：它需要改写现有 AudioBuffer 预加载、精确起播偏移和自定义循环逻辑，而且 `timeupdate` 跳转可能破坏循环连续性。若将来需要覆盖缺少 AudioWorklet 的旧环境，应独立设计并验证此路径。浏览器的 `preservesPitch` 属性本身定义为变速时补偿音高：[MDN：HTMLMediaElement.preservesPitch](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/preservesPitch)。

若两条路径均不可用，经典音频模式应停留在原速或提示当前浏览器不支持保音高变速。不要回退到会让音高改变的直接变速。

## 7. 备选方案比较

| 方案 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- |
| 直接改 `playbackRate` | 无新依赖、代码简单 | 速度变化会带来升降调 | 不满足需求 |
| `<audio>` + `preservesPitch` | 浏览器负责音高补偿 | 需要重做 BufferSource 的缓存、偏移和循环管理；当前决定暂不启用 | 旧环境的后续备选 |
| AudioWorklet 时间拉伸 | 保留现有 AudioBuffer/Web Audio 管线，可控制算法和实时参数 | 新增依赖、Worklet 注册和延迟/循环适配；需要试听调优 | **推荐主路径** |
| 预制多个 BPM 音频 | 播放稳定，运行时 DSP 开销小 | 文件体积和制作维护成本增加；任意 BPM 仍需选择/插值 | 当前单曲与实时滑动场景不优先 |

## 8. 验收标准

- 在 60、90、125、150、180 BPM 各试听至少一个完整循环，主观听感不再随 BPM 升降调。
- 有持续音符的参考片段在变速后音高稳定；建议用频谱/调音器比较原速和各目标速率，确认偏差在项目设定容差内（初始建议 ±25 cents，试听后校准）。
- 音乐首拍与节拍指示、和弦切换保持同步，无明显启动滞后。
- 起播仍从配置偏移开始，循环处无明显点击、空洞或节奏错位。
- BPM 滑动时不重启播放、不爆音、不明显卡顿；停止、重播、切换模式后无残留声音。
- 在桌面 Chrome、Safari，以及项目支持的 iOS Safari/Android 浏览器上验证主路径或降级路径；不支持时给出清晰反馈且不升降调。
